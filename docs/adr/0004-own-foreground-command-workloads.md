# Own foreground command workloads before adding inactivity

The first service slice supports command services and finite startup actions. Each entry has a stable ID, an explicit executable and raw Windows arguments, a working folder (entry override or project folder), an optional normal-stop command, and a shutdown deadline. Commands inherit the user's environment and receive noninteractive stdin. Shell scripts require an explicitly configured shell. Compose, environment overrides, dependency scheduling, and TCP/HTTP readiness are follow-up slices; the initial readiness rule is process running.

Saved settings use schema 3. Versions 1 and 2 migrate in memory; loading does not rewrite the original file. A live session owns a copied workload setup. Save does not change its Start/Retry or shutdown commands. Switch does not rerun completed actions or restart manually stopped services. Deliberate relaunch stops old workloads with the old setup before using the new setup. Close and relaunch retain the old session if any workload cannot stop.

On Windows 11, create each foreground command in a private Windows Job Object using `PROC_THREAD_ATTRIBUTE_JOB_LIST`. This establishes job membership during process creation, before the command can launch children. Use `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` to inherit only the stdin and combined stdout/stderr pipe handles. Retain creation-returned process and job handles; never establish ownership by process name, PID, or port. Do not enable breakaway or kill-on-job-close limits. See Microsoft's [job documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [process creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

Job accounting, rather than just the launcher process, determines whether an owned workload remains live. A launcher that exits while children remain cannot authorize a replacement. Startup action completion requires an empty job and a successful launcher exit; a command service exiting, including with code zero, is reported as an unexpected exit. Brokered processes, detached Docker workloads, and external services are not brought into ownership by a successful command exit. Use startup actions only for finite commands whose exit status correctly reports their work.

Retain the latest 64 KiB of combined output per start attempt and another 64 KiB for its most recent stop command. Read fixed-size chunks rather than unbounded lines, and mark omitted bytes. Output is in memory and is not a durable log. The UI worker checks only owned job state and pending output every 500 ms while those resources are active. With no active workload or pending pipe data, it blocks on events. This avoids continuous full-window scans but still needs resource measurements with real workloads.

Normal Stop runs the session's configured stop command in its own owned job and waits for both the workload and stop command to exit. The default deadline is 10 seconds, configurable from 1 to 3600 seconds. A missing command, failed command, or timeout leaves surviving processes owned and running. No automatic escalation is allowed. A still-running previous stop command prevents launching another stop command. Explicit Force stop terminates only the selected workload job and its stop-command job, including their owned children. Other services can complete shutdown even when one fails.

Stop operations run on the workspace worker, so the UI remains responsive while workspace operations are serialized. The first slice reports the result after the bounded wait; cancellation and richer shutdown progress remain follow-up work.

The accepted leave-running exit requires durable output handling and verified reconnection. This slice keeps Quit blocked while managed jobs are live and provides **Stop services and quit** instead. It keeps Jurabox open on any stop failure or newly edited unsaved form; the tray action shows the manager so progress and failures remain visible. Closing the manager still hides it to the tray. This is a temporary delivery boundary, not removal of the planned leave-running exit. Pipe capture cannot guarantee surviving workload behavior after a crash or external process termination; recovery remains unimplemented. Do not add inactivity-driven shutdown until these lifecycle boundaries are validated.
