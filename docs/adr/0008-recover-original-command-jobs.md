# Recover original command jobs after host failure

ADR 7 preserves live services across a manager exit while the session host survives. A host crash loses those retained handles. Blocking every command-only session indefinitely is too restrictive, but a saved PID, executable path, or responding endpoint cannot establish ownership of surviving children.

For recorded command services and startup actions, create a randomly named Windows job and save its capability before creating any process. Use `Global\Jurabox.Command.<random UUID>` with owner/SYSTEM access, reject an already-existing object on creation, and continue assigning the job during `CreateProcessW` before user code executes. Do not enable breakaway or kill-on-close. Internal diagnostic and Docker client commands continue using unnamed jobs.

Windows keeps a job object alive until its last handle is closed and all associated processes terminate, but the development-host crash test showed that its name disappeared at last-handle close while child processes survived. A saved random name alone therefore cannot establish either recoverability or termination.

Use one additional query-only Rust command keeper per launching host. It opens each original job and acknowledges its retained handle before the host may create that workload. A separate Arm message follows the creation attempt; owner-pipe EOF also arms pending registrations after a crash. The keeper observes job accounting and flushes a completion seal only after the armed original job has zero active processes, while its exact handle remains open. It then releases that job. It neither creates nor terminates workloads, requests no terminate rights, and sleeps without polling when it has no jobs. Communication uses private anonymous stdio pipes, bounded JSON frames, and a finite registration acknowledgement deadline. A detached keeper exits once its jobs are sealed. This is same-binary lifecycle isolation, without another language or service installation.

A replacement host may use `OpenJobObjectW` with only query/terminate rights for the original saved capability. This extends ADR 4's creation-handle rule with a private creation-recorded job capability; it does not permit arbitrary job-name, PID, executable, port, or process-tree adoption. Global naming prevents a different Windows login session from hiding a surviving original job. The random capability and owner ACL keep different users and projects separate. Same-user tampering with private records is outside this trust boundary.

Keep atomic, bounded, flushed runtime records separate from saved project definitions. A workspace manifest commits a fresh session generation and its original setup only after all service records are initialized, and before startup scheduling begins. Each actual start and stop-command launch flushes a fresh capability before process creation. Polling records completed/manual-stop state without rewriting unchanged service records. Missing or unsupported records fail closed; a crash between session intent and manifest commit can therefore require manual resolution even if nothing launched.

The host's exclusive lock remains the authority for starting a replacement host. Version 2 journals permit command-only recovery; version 1 open-session records lack sufficient proof. Read the original workspace manifest, reopen only recorded surviving jobs, validate persisted window incarnations, and retain original desktop GUIDs when still present. Restore successful completed actions and manual stops. Cancel queued startup and require explicit Retry for network readiness. Never launch an app, service, dependent, or stop command during recovery. An interrupted stop remains a stop failure until the user resolves it.

If the original job has disappeared with a valid completion seal, report it ended and require explicit Start/Retry. A missing job without that evidence remains uncertain and blocks replacements; losing both host and keeper must never be mistaken for termination. If an action ended while the host was down, its success is unknown unless successful completion had already been recorded; do not infer success or automatically rerun it. A recovered job can remain live through owned children even after its original launcher exits. Force stop still acts only on that exact job handle.

Once command quiescence has been verified, and no verified windows or original desktop survive, end the old command-only session without launching anything. The next deliberate Open uses the latest saved setup. A sudden reboot/logoff can lose an unsealed keeper and job together; that remains blocked rather than inferred from resource absence. Reliable boot/session identity and an in-app resolution flow are follow-up work. A diagnostic that stops commands before losing their desktop and host is not a real reboot test.

Bounded output pipes and root exit handles are not recoverable after host death. Clearly mark output unavailable for that recovered instance, and treat an unrecorded final exit result as unknown. Services that require their stdout pipe to remain connected may exit with the host; report them missing. Durable bounded output is separate work.

This phase deliberately refuses lost sessions containing Docker Compose, including mixed command/Compose sessions. Container recovery requires the original engine, owner nonce, full creation identities, frozen setup, and write-ahead create state. Preserve those uncertain journals rather than creating replacement containers. Automatic runtime-record/snapshot cleanup and an in-app resolution flow for legacy/uncertain records remain follow-up work.
